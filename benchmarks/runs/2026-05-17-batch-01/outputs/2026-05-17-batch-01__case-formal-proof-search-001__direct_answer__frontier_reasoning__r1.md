## Direct answer

The recommended output is a **proof-search state map**, not a theorem verdict. Because the case description gives no concrete object-language formulas, the safe direct answer is to separate the state into six buckets and forbid cross-contamination between them: **axioms**, **claims**, **proof obligations**, **countermodel tests**, **unknowns**, and **update triggers**. In particular, the candidate lemma must remain a **claim** until it is independently proved, and any incomplete proof step must remain a **proof obligation** or **unknown**, never an axiom. ## Evidence-tagged map

Use the following notation throughout the map: `A` = trusted premises; `G` = main goal; `L?` = candidate lemma; `C_i` = intermediate branch claims; `O_i` = open proof obligations; `K_i` = countermodel tests; `M_i` = concrete countermodel witnesses; `U_i` = explicit unknowns.

**Axioms.** Put only the trusted base here: stated axioms, definitions, typing context, imported rules, and already-established theorems from the formal environment. Keep this bucket intentionally small. Do **not** place `L?`, any intermediate `C_i`, or any generated side condition here merely because they would make the proof go through. This follows the same structural distinction formal tools make between assumptions and targets to be checked. citeturn9view0turn6view0turn2view2

**Claims.** Put the target theorem `G`, the candidate lemma `L?`, and every bridge claim `C_i` in this bucket. Each one should carry an evidence tag chosen from: `proved`, `open`, `bounded-clean`, `refuted`, or `unknown`. A claim remains `open` until it has its **own** proof. A claim moves to `refuted` when a genuine model of `A ∧ ¬claim` is found; if the search was bounded, tag it more carefully as a **bounded refutation**. Alloy’s `check` command is defined in terms of finding a counterexample to an assertion, and Mace4 is designed to search for structures that satisfy the denial of a conjecture. citeturn9view0turn8view1

**Proof obligations.** Create explicit obligations rather than leaving them implicit in prose. At minimum, define `O_goal : A ⊢ G`, `O_lemma : A ⊢ L?`, and for each branch step `C_i`, define `O_step_i : A ∪ proved(prefix_i) ⊢ C_i`. Add separate side-condition obligations such as typing, coverage, coercion, termination, or well-formedness checks. This is exactly the kind of separation used by interactive and VC-oriented systems: Coq explains tactics as replacing a goal by subgoals, `eapply` leaves existential variables for later instantiation, Rocq `Program` generates obligations, and Why3 generates proof obligations for side conditions such as non-exhaustive pattern matches. citeturn5view0turn2view2turn2view3

**Countermodel tests.** Attach a dual test to every non-axiom item. Define `K_goal = A ∧ ¬G`, `K_lemma = A ∧ ¬L?`, and `K_step_i = A ∧ proved(prefix_i) ∧ ¬C_i`. Also include `K_consistency = A` to check whether the axiom base itself is satisfiable, plus a vacuity or redundancy test for suspicious assumptions. Isabelle Quickcheck tests current goals by trying assignments for free variables, Nitpick tests current goals for counterexamples using a reduction to first-order relational logic, Mace4 searches finite structures satisfying first-order/equational statements, and Kodkod provides both finite-model finding and unsat-core extraction. Alloy’s unsat-core support is explicitly aimed at detecting inconsistency or vacuously true assertions. citeturn2view1turn2view0turn8view1turn8view2turn10view0

**Unknowns.** Record everything that is unresolved but not yet falsified: missing domain restrictions, unspecified semantics, solver `Unknown`, timeout, insufficient bounds, deferred witness terms, existential variables left open by search, and any side condition that has not been discharged. This bucket is important because “not proved yet” and “probably true” are not the same thing. Why3 explicitly distinguishes `Invalid` from `Unknown`, and Alloy explicitly warns that bounded failure to find an instance does not prove nonexistence, even though any instance it does find is valid. citeturn2view4turn9view0

**Update triggers.** Mark a trigger whenever the axiom set changes, the goal changes, the candidate lemma changes, a countermodel is found, a solver flips an obligation to `Invalid`, or a previously stored proof attempt becomes stale because the underlying task has changed. Why3 explicitly marks proof attempts `obsolete` when the current task differs from the earlier one, which is exactly the behavior this map should mirror. citeturn2view4

## Adapter fit

The right formal adapter depends on the logic fragment, not on convenience. If the task lives in a higher-order setting with datatypes, inductive or coinductive definitions, and quantifiers, a HOL-oriented negative-testing adapter is the right fit: Nitpick is designed for Isabelle/HOL formulas of that kind, and Quickcheck is designed to test goals by instantiating free variables. If the task has strong **finite-model pressure** in first-order or equational form, a finite-model finder such as Mace4 or a relational solver such as Kodkod is the right adapter for the counterexample side of the workflow. If the environment naturally emits verification conditions, a Why3-style VC tracker is the cleanest fit because each task can be recorded separately and marked `Valid`, `Invalid`, `Unknown`, `Timeout`, or `Failure`. None of these tools should be treated as globally “better”; they fit different proof-search geometries. citeturn2view0turn2view1turn8view1turn8view2turn6view0turn2view4

A practical consequence is that the **same candidate lemma may look healthy in one adapter and fragile in another**. For example, a bounded model finder may produce a small counterexample rapidly, which is strong negative evidence; by contrast, failure to find a counterexample inside a bound is only weak positive support. That is why the map should always store both the **test result** and the **completeness condition** under which the result was obtained. citeturn9view0turn8view1turn8view2

## Countermodel handling and kill tests

A failed proof path should not merely be annotated as “stuck”; it should be subjected to **kill tests**. The first kill test is the **lemma kill test**: run `A ∧ ¬L?`. If that task has a model, every branch that uses `L?` is dead and should be pruned immediately. In a finite bounded setting, record the scope and tag the result as a bounded refutation rather than an absolute one. Mace4, Alloy, Nitpick, and Quickcheck all support this general style of “search for a witness to failure” rather than “wait for proof search to get lucky.” citeturn8view1turn9view0turn2view0turn2view1

The second kill test is the **bridge-step kill test**: for each intermediate step `C_i`, test `A ∧ proved(prefix_i) ∧ ¬C_i`. This isolates where the branch actually breaks. If a model exists there, the problem is not “the final theorem is hard”; the problem is “this step is false or under-specified.” Coq’s description of tactics as reducing goals to subgoals, together with Why3’s explicit per-task statuses, supports this fine-grained treatment of proof state rather than monolithic pass/fail reasoning. citeturn5view0turn2view4

The third kill test is the **contradiction or vacuity test**. Check whether `A` is itself inconsistent, or whether the proof is succeeding only because some assumptions make the goal vacuous. Alloy’s unsatisfiable-core tooling is explicitly documented as a way to detect specification inconsistencies and vacuously true assertions, and Kodkod similarly exposes unsat-core extraction. Isabelle also exposes `find_unused_assms`, which is useful for detecting assumptions that are not genuinely load-bearing. citeturn10view0turn8view2turn2view1

The fourth kill test is the **non-proof test**: `Unknown`, `Timeout`, or “no counterexample found within current bounds” must never be promoted to proof. Why3 makes the `Unknown` status explicit, and Alloy states plainly that bounded failure to find an instance does not imply that none exists. So the rule is simple: those outcomes may keep a branch alive, but they do not validate it. citeturn2view4turn9view0

## Update behavior

If the candidate lemma is disproven, the answer changes immediately and materially. The lemma leaves the claims bucket and is marked **refuted**. Every proof branch that depends on it, directly or transitively, loses evidential force and should be retired rather than patched by silently inflating the axiom set. The discovered countermodel becomes a standing regression test against future reformulations of the lemma or goal. The next move is then one of three repairs: weaken the lemma, split it into narrower obligations, or justify an additional premise independently and explicitly. Branches that never depended on the disproven lemma remain open. This is the same basic logic behind counterexample-guided debugging in formal tools and behind Why3’s practice of replaying proofs when the underlying task changes. citeturn8view1turn9view0turn2view4

If later evidence shows that the earlier countermodel was only a bounded artifact or an encoding mismatch, the map should not revert blindly. Instead, the countermodel should be reclassified from “refuted” to “boundedly refuted or adapter-specific,” the branch should be reopened, and the corresponding obligation should be replayed under the corrected semantics. If the axiom base or goal statement is edited, earlier proof attempts should be treated as stale until replayed on the new task. citeturn9view0turn2view4
